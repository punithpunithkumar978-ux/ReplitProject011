# 1. APPLICATION IDEA

Build a smart digital queue/token management platform.

The main problem:

People currently have to physically stand in long queues to access services such as:

* Hospitals
* Clinics
* Government offices
* Banks
* College offices
* Restaurants
* Service centers
* Salons
* Customer service counters
* Labs
* Ticket counters
* Other organizations that operate using physical queues

The application allows a person to:

1. Find a service/location.
2. Select the required service.
3. Request a digital token.
4. Receive a token number.
5. See the approximate waiting time.
6. Track their position in the queue.
7. Receive notifications when their turn is approaching.
8. Arrive at the location near their expected service time instead of standing in a physical queue.

Organizations can:

1. Create their organization.
2. Create service counters/services.
3. Configure queue rules.
4. Generate and manage tokens.
5. Call the next token.
6. Skip absent customers.
7. Mark customers as completed.
8. Monitor queue statistics.
9. View current queue status.
10. Manage staff/operators.

# 7. TOKEN GENERATION

Token numbers must be generated safely.

Do not rely only on frontend JavaScript to calculate:

lastToken + 1

because simultaneous customers could receive duplicate tokens.

Token generation should be handled safely at the database/backend level.

For each organization + service + queue date:

Example:

A001
A002
A003
A004

or:

1
2
3
4

Choose a simple token format for MVP.

Prevent duplicate token numbers under concurrent requests.

Use PostgreSQL constraints/functions/transactions where appropriate.

---

# 8. QUEUE LOGIC

The queue should generally operate in FIFO order.

Example:

Token 1
Token 2
Token 3
Token 4

If Token 1 is being served:

Current:
Token 1

Waiting:

Token 2
Token 3
Token 4

When staff presses:

"Call Next"

Token 2 becomes called/serving.

When completed:

Token 2 becomes completed.

Then:

Token 3 becomes next.

Do not allow invalid state transitions.

For example:

completed → serving

should not be allowed.

# 9. ESTIMATED WAITING TIME

For MVP:

Estimated wait time can be calculated using:

number_of_people_ahead × average_service_time

People ahead = 5

Display:

Clearly label this as an estimate.
